# 番号体系仕様メモ

作成日: 2026-06-19
対象: 注文・納品・請求の内部ID / 表示番号 / 採番責務

## 1. 方針

- DB主キーは各エンティティとも UUID を採用する
- 人間向けの表示番号は UUID とは別に持つ
- 表示番号の採番責務は原則 BE に持たせる
- 注文・納品・請求を横断して追跡するため、共通の案件トラッキング番号 `tracking_no` を持つ
- 経理向け正式請求書番号は、ドラフト用番号とは別に持つ

## 2. UUID を使う対象

- 注文ヘッダー: `order_id`
- 注文明細: `order_item_id`
- 納品ヘッダー: `delivery_id`
- 納品明細: `delivery_item_id`
- 請求ヘッダー: `invoice_id`
- 請求明細: `invoice_item_id`

用途:

- DB主キー
- API内部参照
- 外部システム連携キー
- 監査ログ・更新整合性の基準キー

## 3. 共通案件トラッキング番号

### 3.1 定義

- 注文・納品・請求をまたいで同一案件を追える共通番号
- 形式は `YYYYMMDD-XXXXX`

例:

- `20260619-00042`

### 3.2 採番ルール

- `YYYYMMDD`: 採番日
- `XXXXX`: 当日5桁連番

### 3.3 採番タイミング

- 注文ヘッダー作成時

### 3.4 採番責務

- BE

### 3.5 運用ルール

- 欠番は許容する
- キャンセル後も再利用しない
- この番号は経理連番ではなく、業務トラッキング用とする

## 4. 各表示番号の仕様

### 4.1 注文ヘッダー番号

- カラム候補: `order_no`
- 形式: `ORD-YYYYMMDD-XXXXX`
- 例: `ORD-20260619-00042`
- 生成タイミング: 注文ヘッダー作成時
- 採番責務: BE
- 役割: 受注業務上の代表番号

### 4.2 注文明細行番号

- カラム候補: `order_line_no`
- 形式: `ODL-XXXXX-ZZZZ`
- 例: `ODL-00042-0001`
- `XXXXX`: 親注文の共通案件番号の連番部分
- `ZZZZ`: 親注文内の明細連番
- 生成タイミング: 注文明細作成時
- 採番責務: BE
- 役割: 人間向けの明細識別番号

### 4.3 納品ヘッダー番号

- カラム候補: `delivery_no`
- 形式: `DLV-YYYYMMDD-XXXXX-SS`
- 例: `DLV-20260620-00042-01`
- `SS`: 同一案件内の納品枝番
- 生成タイミング: 納品ヘッダー確定時
- 採番責務: BE
- 役割: 納品単位の表示番号

### 4.4 納品明細行番号

- カラム候補: `delivery_line_no`
- 形式: `DLI-XXXXX-SS-ZZZZ`
- 例: `DLI-00042-01-0003`
- 生成タイミング: 納品明細作成時
- 採番責務: BE
- 役割: 納品明細の表示番号

### 4.5 請求ヘッダー番号（ドラフト/システム管理用）

- カラム候補: `invoice_draft_no`
- 形式: `IVD-YYYYMMDD-XXXXX-SS`
- 例: `IVD-20260621-00042-01`
- 生成タイミング: 請求ドラフト作成時
- 採番責務: BE
- 役割: 請求ドラフトやシステム内部確認用番号

補足:

- 現在の `DRAFT-...` は廃止し、ドラフト番号プレフィックスは `IVD-` を採用する
- `INV-` は正式請求書番号と混同しやすいため、ドラフト用途では使わない

### 4.6 請求明細行番号

- カラム候補: `invoice_line_no`
- 形式: `IVL-XXXXX-SS-ZZZZ`
- 例: `IVL-00042-01-0002`
- 生成タイミング: 請求明細作成時
- 採番責務: BE
- 役割: 請求明細の表示番号

### 4.7 正式請求書番号（経理・取引先向け）

- カラム候補: `official_invoice_no`
- 形式: `INV/YYYY/NNNNN`
- 例: `INV/2026/00001`
- `NNNNN`: 年単位5桁連番
- 生成タイミング: 請求ヘッダー確定時
- 採番責務: BE
- 役割: 経理・取引先向け正式番号

運用ルール:

- 欠番管理対象はこの正式請求書番号のみ
- ドラフト削除・再作成では採番しない
- 一度採番した正式番号は再利用しない

## 5. この設計の狙い

- UUID で内部整合性を担保する
- 表示番号で現場運用の分かりやすさを担保する
- `XXXXX` 共通化で注文/納品/請求のつながりを直感的に把握できる
- 正式請求書番号を別管理にすることで、欠番管理と監査対応を経理要件に寄せられる

## 6. 懸念点と対策

### 6.1 1注文から複数納品・複数請求が発生する

- 問題: `XXXXX` だけでは一意に見分けられない
- 対策: `SS` 枝番を持つ

### 6.2 複数注文をまとめて1請求にしたい

- 問題: 1つの請求に複数 `tracking_no` がぶら下がる
- 対策候補:
  - MVPでは「1請求 = 1 tracking_no」に制限する
  - 将来は請求ヘッダーに代表 `tracking_no` を持ち、明細ごとに元 `tracking_no` を保持する

本件は業務ルール未確定なら、MVPでは前者を推奨する。

### 6.3 キャンセルや作り直しが頻繁

- 問題: 欠番が出る
- 対策: `tracking_no` 側は欠番許容とし、正式請求書番号だけ厳格管理する

## 7. MVP推奨

MVPでは以下を優先する。

- UUID主キー化
- `tracking_no` 導入
- `order_no` / `order_line_no` / `invoice_draft_no` / `invoice_line_no` 導入
- `official_invoice_no` 導入
- 納品ヘッダー/納品明細は独立実体を作るタイミングで番号体系を適用
