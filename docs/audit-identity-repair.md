# 注文保存失敗の修復（2026-09-18）

## 原因

注文作成は一覧の表示漏れではなく、監査ログINSERT時のNOT NULL違反で409となり、注文全体がロールバックしていた。
過去の `2026061904_uuid_primary_keys_for_orders_and_invoices.py` がPostgreSQLで
audit_logsを `id INTEGER NOT NULL PRIMARY KEY` として再作成し、自動採番を失っていた。
SQLiteのINTEGER PRIMARY KEYやORMから新規生成したテーブルでは再現しないため、従来テストでは検出できなかった。
注文取消にも同じ障害を確認した。

## 修復

- 新規マイグレーション `2026091801_restore_audit_log_identity.py` を追加。過去の適用済みマイグレーションは変更しない。
- PostgreSQLのみ、採番設定がない場合にGENERATED BY DEFAULT AS IDENTITYを追加。
- テーブルを排他ロックし、既存IDの最大値+1（最低1）から開始する。
- 既存のdefault/identityは変更しない。SQLiteは変更不要。
- downgradeでも修復は保持する（再び書き込み不能になることを防ぐデータ修復）。
- 業務API、認証、Frontendは変更しない。

## 適用

アプリ停止後にpg_dumpでバックアップし、pg_restore --listで読み取り確認した。
ホスト側バックアップ: `.local/backups/before-audit-identity-20260918.dump`（権限600、共有禁止）。
稼働DBに2026091801を適用済み。
適用前後で注文11件、顧客7件、監査ログ1198件、認証ユーザー2件が維持された。
テスト注文やテストユーザーは稼働DBに作成していない。

`backend/tests/test_audit_identity_migration.py` を追加。
専用PostgreSQL DB `order_system_v2_audit_repair_test_20260918` を使用し、
テストごとに専用スキーマを作り、終了時にトランザクションをロールバックする。
実データやpublicテーブルは使わない。

- 自動採番欠落によるINSERT失敗の再現。
- 空テーブルと既存データありの採番修復。
- 既存データ保持、再実行時の巻き戻り防止、既存SERIAL設定保持。
- PostgreSQLで実際の注文作成・一覧取得・取消ルート関数と監査記録を確認。
